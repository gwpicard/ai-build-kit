AI Build Kit helps a person build and run a tool with a coding agent, without needing to read code. It is for people who are comfortable with technology but do not write code. Team leads, operations staff, analysts, product managers and founders may use it. A developer who is new to agent-led work may use it too.

## Why the kit exists

A coding agent can make a working tool quickly. Many such tools are prototypes. Six weeks later, nobody may know how to change one safely, where its data lives, or what to do when it fails.

A hosted app builder can be fast, but the tool stays on that platform. A developer's kit can make work reliable, but it expects the person to read code. AI Build Kit is designed for the space between those options. The project stays in accounts the owner controls. The person can change coding agent, host or developer later.

The kit suits internal tools used by people the owner names, such as a team, a club, a family or invited clients. Its proven setup keeps each tool private by default. Public features are possible when the person asks for them, hears the risks and records the choice. A tool that takes money from strangers is public-facing.

The kit does not suit someone who wants an app in ten minutes and never wants to use GitHub. A hosted builder may suit them better. The kit is not a way to learn programming. It does not replace a developer when one is needed. It does not run a service of its own or keep project records outside the person's project. A project may need a professional for work that calls for one.

## How the work is controlled

The person agrees on one piece of work at a time. A piece has a result that can be checked. The kit records each piece with the project, then an agent builds it. The person tries the result and decides whether to approve the change for merge. A merge puts the change into the main version. On a hosted project, that can put it live.

The person creates and owns the accounts. The code stays in their repository, the tool runs on their host account, and its data stays in their database account. The kit does not create these accounts. It runs no hosted scanning or monitoring. A recipe names any service the tool uses, and the owner holds those accounts.

The kit uses a machine rule wherever a machine can hold a promise. A hook, a setting or a script applies the rule every time. Prose explains only the judgements a machine cannot make. This keeps the instructions shorter and makes the rule less dependent on which coding agent the person uses.

At setup, the kit records what failure could cost. It asks who could be affected, what data the tool holds and how the owner could recover. It also names the kinds of risk that apply. Each piece then names the risk areas it touches. The kit warns about a risk, then lets the person decide what to do. It records that choice and does not ask again or refuse the work. Some rules protect every project. A person cannot waive those rules.

## How the kit is checked

Shell checks test boundaries, files and scripts. They run quickly and fail when a required boundary or result is missing.

Replays run a recorded conversation in a temporary project. A grader checks what the agent did and what it left on disk. The results show how often the kit met its promises across several runs.

The mutation run breaks one promise at a time. It reports which checks notice the broken promise.

Release verification builds the release again and compares it with the version prepared for publication. This checks that the files ready to ship match the reviewed release.

The kit removes rules that do not help. A rule stays in the instructions when a machine enforces it, evidence shows it improves results, or it asks for judgement that only a person or agent can make. A rule based on one failed run stays a guess until a measurement supports it.

The person does not need to read code to use the process. Each check gives a result the person can see or try, and each report says what was checked. A developer may read each change if they choose. The kit does not depend on that because the process must work when nobody reads the code.

These checks give evidence about the kit. They do not prove that every tool built with it is safe or right for every purpose. A check that did not run never counts as a pass.
