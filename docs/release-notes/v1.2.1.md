v1.2.1 changes the wording of the kit's messages, reports and records: a merge, an upload or a live change now requires your approval rather than "a yes", and the agent describes checks and results in more precise terms.

**Who gets what.** Every project that updates gets the changes to the skills and to the messages the kit's scripts print. The new wording in the project instructions file, `AGENTS.md`, and in the opening text of `CHANGELOG.md` reaches new projects only, because an update does not rewrite either file in an existing project. The tidying of v1.2.0's files in item 5 applies only to projects founded from a whole copy of the kit.

## Updating

Run `/maintain` to update an existing project. Then start a new session, so the agent reads the new skills. No other action is required, and no project data changes.

## What changes

1. **"Approval" replaces "a yes".** The skills, `WORKFLOW.md` and the messages the merge script prints now say that a merge, an upload or a live change requires your approval. The rules have not changed. Approval must still name the action, and approval to build, save, upload, go live or set up hosting still does not count as approval to merge. The setup check's two summary lines are reworded in the same way.
2. **A shorter access question.** `/maintain` asks a project whose plan records no access choice which access setting to record. That question is now split into short sentences. It still only records your answer and runs the access check. Changing the live tool still needs separate approval.
3. **Precise wording instead of forced simple words.** New projects' instructions ask the agent to report what it achieved precisely and naturally, and to use the established term where it is the right word, defining it once if you may not know it. The agent describes a check by what it does: it detects, reports, blocks or skips. It claims only what the evidence shows. While shaping work, `/clarify` uses your own terms in the same way.
4. **Better changelog entries, pull request descriptions and piece titles.** In every project, the agent writes each changelog entry from the finished work, saying what changed and why, and checks it against what the piece set out to do. A pull request description states what changed, why, how it was checked and what was not checked. A piece's title names the change precisely.
5. **Tidying the kit's own files from v1.2.0.** In a project founded from a whole copy of the kit v1.2.0, `/maintain` can now offer to remove the kit's own files at the project root, such as `WORKFLOW.md` and the plugin folders, when they match v1.2.0 exactly. Before, it could only name them. A file you changed is left alone.

## What was tested, and what is not proven yet

- The source checks, the adapter checks and the full set of rehearsals on a clean copy pass on GitHub.
- A replay of six recorded conversations checked the merge and upload approval steps with the new wording. Four behaved as before, with no false alarms. In the two that apply a live database change, the agent asked for approval correctly, but the test harness did not recognise the command it then ran, so the change was never applied. Those two steps are not proven by replay for this release.
- No replay measured whether the agent's reports in a new project read better. That effect is not measured yet.
