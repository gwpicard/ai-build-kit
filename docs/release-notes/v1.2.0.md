v1.2.0 gives new projects on both Next.js recipes a proper front end and a project check that runs on GitHub. It also lets an approved merge go ahead when a GitHub billing limit alone stopped the check.

## Updating

Type `/maintain` in your project and accept the kit update through your existing installation route. Start a new session afterwards so it reads the new skills. Nothing else is needed, and no data changes.

The front end and the GitHub workflow below come with the starter. A project started before v1.2.0 keeps its own pages and checks. The update does not add them to it.

## What changes

- A new project on either Next.js recipe starts with shadcn/ui components on Radix, and with the design colours in one file. The sign-in, invitation and owner setup pages use these components. Each field has a visible label, and each control shows where focus is.
- The project check now fails when code goes around the design. It refuses colours that are not design colours, unknown or conflicting style classes, and plain buttons, text fields and drop-down lists outside the components folder. Each message says what to use instead.
- An accessibility test runs on the sign-in page with the other browser tests. It also checks that each label is visible and that focus shows.
- A new recipe project gets a `recipe-check` workflow on GitHub. On each pull request and each push to `main`, it builds a local database from the migrations. Then it runs the type check, lint, unit tests, the build, the row rules check and the browser tests. Branch protection requires it next to `project-check`.
- When GitHub did not start `project-check` only because of a billing limit, an approved merge now runs that check on your computer, on a clean copy of the exact commit. A pass lets the merge go ahead, and the agent says that the check ran on your computer. A failed check, another blocked check or an unattended run still holds the merge.
- The second opinion now reads the type and lint results from `recipe-check` when a project has it. Before, it could report them as passed while `recipe-check` had failed. The merge itself was never affected, because a failed or missing check always held it.
- Before a merge, the agent says whether the merge also puts the change live, and names the separate step when it does not.
- The starter's test tools and zod are updated, and both package audits are clear.
- The documentation now states only what each script checks. For example, the row rules check finds tables without row-level security, but it does not prove that their rules restrict access.

## Evidence and limits

The source checks pass. On this computer, one rehearsal fails because a Python test tool is missing, and it fails the same way on the previous release. In a replay, the agent built a leave request form with `/implement` on a new project, in twelve runs. It used the project's components in every run.

The GitHub workflow has not yet had a real run in a project, and its time on GitHub is not measured. The local copy of `project-check` uses your computer's own tools, so its result can differ from GitHub's.
