v1.2.0 gives new projects a shared set of interface components and a GitHub workflow for recipe checks. It also adds a local fallback when billing prevents `project-check` from starting.

**Most of this is for new projects.** Points 1 to 4 and the last item of point 6 come with the starter that a new project on either Next.js recipe (Vercel or Coolify) is built from. A project started before v1.2.0 keeps its own pages and checks, and the update does not add these to it. The rest reaches every project.

## Updating

Type `/maintain` in your project and accept the kit update through your existing installation route. Then start a new session, so the agent reads the new skills. Nothing else is needed, and none of your data changes.

## What changes

1. **New projects start with shadcn/ui components.** These include buttons, text fields, forms, tables, dialogs and drop-down lists. Colours are defined centrally, and the sign-in, invitation and first-owner setup pages use the shared components.

2. **Lint rules enforce shared components and named design colours.** Outside the shared component folder, the rules reject raw form controls and restricted Tailwind colour classes, and explain what to use instead. These checks cover specific code patterns; they do not assess the overall design.

3. **Browser tests now include a basic accessibility check of the sign-in page.** The test looks for common accessibility problems, checks that the email field has a visible label and verifies focus indicators on the email field and submit button during keyboard navigation. It does not prove that the whole tool is accessible.

4. **New recipe projects get a `recipe-check` workflow on GitHub.** On each pull request and push to `main`, it creates a local database from the migrations, checks database types and code, runs unit tests, builds the tool, checks for missing row-level security rules and runs browser tests. Where branch protection is available, setup requires `recipe-check` alongside `project-check` before merging. The row check detects missing protection; it does not prove that the rules are correct.

5. **An approved merge can run `project-check` locally when billing alone prevents it from starting on GitHub.** The kit runs the check's steps on a clean copy of the exact commit and reports that they ran locally. A local pass allows the approved merge to continue. This fallback does not cover `recipe-check`, a failed check, another blocked check or an unattended merge.

6. **Smaller corrections.**
   - The reviewer now reads type-checking and linting results from `recipe-check` when present. Previously, it could report those checks as passed when `recipe-check` had failed. The merge gate already blocked failed checks; this fix corrects the review report.
   - Before each merge, the agent now says whether that merge also puts the change live. When it does not, the agent names the separate step that does.
   - The documentation now promises only what each check really proves. For example, the table check finds tables with no protection on their rows, but it does not prove that the protection is right.
   - New projects get newer versions of the test tools and of the library that checks form input. Both dependency audits reported no known vulnerabilities when the release was prepared.

## What we tested, and what is not proven yet

- All of the kit's own checks pass on GitHub.
- We asked the agent to build the same leave request form on a new project, twelve times. Each run used the shared interface components.
- The new `recipe-check` workflow has not yet run on GitHub in a real project, so its runtime there is unmeasured.
- The local `project-check` fallback uses your computer's tools, so its result can differ from a run on GitHub.
