v1.2.0 makes new projects look better and catch more mistakes before they go live.

**Most of this is for new projects.** Points 1 to 4 and the last item of point 6 come with the starter that a new project on either Next.js recipe (Vercel or Coolify) is built from. A project started before v1.2.0 keeps its own pages and checks, and the update does not add these to it. The rest reaches every project.

## Updating

Type `/maintain` in your project and accept the kit update through your existing installation route. Then start a new session, so the agent reads the new skills. Nothing else is needed, and none of your data changes.

## What changes

1. **New projects start with a proper look and feel.** A new project has a ready set of screen parts: buttons, text fields, forms, tables, pop-ups and drop-down lists. They come from shadcn/ui, a widely used free collection. The colours are set in one place, so every page matches. The sign-in, invitation and first-owner setup pages already use these parts.

2. **The project checks itself for design mistakes.** If a page uses a colour outside the set, or the agent builds its own button instead of using the ready one, the project check fails. The message says what to use instead. This keeps the screens consistent as the project grows, so it does not drift into a patchwork look.

3. **A basic accessibility check.** Each time the browser tests run, which GitHub does for every change, they test the sign-in page for common accessibility problems. The test also checks that each field has a label you can see, and that you can see where you are when you move through the page with the keyboard. This is a basic check. It does not prove that the whole tool is accessible.

4. **GitHub tests every change.** A new project has a full check on GitHub, called `recipe-check`, that runs for every change. It builds a test copy of the database, checks the code, runs the tests, builds the tool, checks that each database table protects its rows, and clicks through the pages in a real browser. A change cannot merge until this check passes.

5. **A billing limit no longer blocks a merge.** Sometimes GitHub does not run the project check because of a billing limit on the account. Before, the merge was stuck. Now, when you approve the merge, the same check runs on your computer instead, and the agent tells you that it ran there. A failed check, any other check that did not run, or a merge with nobody watching still stops the merge.

6. **Smaller corrections.**
   - The reviewer agent could report that the code checks had passed when the GitHub check had failed. This is fixed. Merging was always safe, because a failed check still stopped the merge.
   - Before each merge, the agent now says whether that merge also puts the change live. When it does not, the agent names the separate step that does.
   - The documentation now promises only what each check really proves. For example, the table check finds tables with no protection on their rows, but it does not prove that the protection is right.
   - New projects get newer versions of the test tools and of the library that checks form input. These versions have no known security problems.

## What we tested, and what is not proven yet

- All of the kit's own checks pass on GitHub.
- We asked the agent to build the same leave request form on a new project, twelve times. Each time, it used the ready screen parts.
- The new GitHub check has not yet run in a real project. Its first real run will show how long it takes.
- When the check runs on your computer because of a billing limit, it uses your computer's own tools. Its result can differ from GitHub's.
