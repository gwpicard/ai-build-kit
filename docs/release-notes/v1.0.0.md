v1.0.0 replaces build paths with a risk record and adds checks before work can merge or go live.

## Updating

Type `/maintain` in your project and ask for the monthly routine. Older releases check for kit updates there. Accept the update through your existing installation route. For shared skills, the update uses `npx skills add gwpicard/ai-build-kit`. This adds missing skills too. Do not use `npx skills update`.

After updating, start a new session and type `/maintain` again. Ask for the monthly routine on this visit too. The session that ran the update still follows the old release's instructions. The new visit offers the remaining changes. It needs a clean saved checkpoint before applying them. Your unfinished work stays where it is.

The kit no longer uses the old build paths, including private exploration. `/maintain` shows your old section and the proposed risk record before asking to move it. On your yes, it keeps your risk areas, acceptance dates and words. `Sensitive areas` becomes `Risk areas`. The earlier path and reason stay as history.

The move adds risk areas to open pieces where their recorded reach identifies them. Checks that lack information report that limit. They do not claim a pass. The visit then asks the three risk questions to complete the record. If you decline, the kit leaves the old section unread and offers the move again on a monthly visit.

Every project now needs a repository with issues enabled and a session that can read and write them. Setup also checks branch protection and the tools the recipe needs for host and database access. A private repository on GitHub Free can continue with a local push guard. GitHub cannot enforce the project check on that plan. `/maintain` explains the new expectations when moving a project that was private only. It does not move the tool online.

All builds now use pull requests. Newly shaped pieces need a `Risk areas:` line. Write `none` there when no area applies. On projects with code, they also need `Reaches:`. This names the files and other parts the change can affect. `/shape` prepares these fields before marking a piece ready.

`/maintain` offers newer safety settings and each missing or older project check separately. These include secret, test, review and push checks. It also asks which access setting your tool needs. Recording that choice does not change live access. `/setup-hosting` makes a live change after your yes. Older recipe names still work. `/maintain` can update those names or open a piece for a larger recipe change.

The six commands from v0.20.x keep their names. The background skills `change-triage` and `section-builder` are now `triage` and `build-piece`. For older projects, `/start` is now `/setup-ai-build-kit`. `/build` and `/plan` give way to `/shape` for agreeing work and `/implement` for building it. `/fix` uses those same two commands. `/queue` is part of `/implement`, `/sync` is part of `/maintain`, and `/ship` is now `/setup-hosting`. The older background skill `grilling` is now `clarify`.

You can update directly to this release. `/maintain` offers to remove retired skills and correct the kit's command list and file pointers. It leaves your own wording for you to change. For a project still using `plan.md`, the monthly routine offers to move each row into an issue. It removes the old list only after the issues exist. For projects without a `ready` label, it marks qualifying shaped pieces ready. Pieces waiting on questions stay there.

## What changes

- Setup prepares a local project and saves a checkpoint. It uses a pinned starter for the supported recipes. The first code upload waits for your yes.
- New tools start private. The recipe checks who can get in. You can choose public access after hearing its risks.
- Each piece names the risk areas it touches. You hear the caution once and can accept it with your words and date. Acceptance lets the work continue. A run without you present cannot accept on your behalf.
- `/shape` records your decision and finishes the piece. Accepting a risk or an unchecked fact does not start a build. You ask `/implement` to build it.
- Builds check what else a change touches and whether its tests prove the change. Project checks catch silent test edits and unresolved review findings. A review names the exact saved version it read. The kit reports a review it cannot verify as unverified.
- The kit holds a merge when a required check fails or cannot run. Each check says whether it passed, failed, could not run, could not decide or did not apply.
- Hosting uses the recipe's launch checks. A recipe launch needs a confirmed backup and a way back. `/setup-hosting` applies database changes after your yes, before merge. Without a recipe, the kit records your choice after one notice and helps by hand. It cannot guarantee or check that launch.
- You can approve longer runs, parallel builds or automatic merging with recorded limits. Automatic merging excludes repairs and changes to risk areas, database structure or live settings. Required checks still apply.
- `/maintain` now checks for a newer release on every visit. It offers each newer version once. It also scans for secrets and checks branch protection. It reports live-copy gaps and offers `/setup-hosting` for repairs.

## Evidence and limits

The release checks include 111 replay runs of real conversations against this release and v0.20.3. Both used the same model. No case got worse by the test's rule. Founding reaches its checkpoint in cases that stopped before. A database change runs after the person's yes. In that test, v0.20.3 never applied it.

The skills are less than half their old size: 70,164 characters before and 30,177 now. The validator, all 93 shell rehearsals and the release build pass on a clean copy.

Some founding runs still save work in more pieces than planned or fail to divide the plan into pieces. These limits also occur in v0.20.3. When the starter command is blocked, founding stops and asks, by design. Runs on real hosting accounts were not part of this release's checks.
