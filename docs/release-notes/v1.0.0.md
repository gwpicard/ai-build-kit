v1.0.0 replaces the old build paths with a risk record, and adds checks that must pass before work can merge or go live.

**Who gets what.** Every updated project gets the revised skills and merge rules. Existing projects receive offers to migrate their build-path record and install missing checks through `/maintain`, with your approval. Projects still using `plan.md` also receive the migration described under Updating.

## Updating

1. Type `/maintain` in your project and ask for the monthly routine. Older releases check for kit updates there.
2. Accept the update through your existing installation route. For shared skills, the update uses `npx skills add gwpicard/ai-build-kit`. This adds missing skills too. Do not use `npx skills update`.
3. Start a new session and type `/maintain` again. Ask for the monthly routine on this visit too. The session that ran the update still follows the old release's instructions. The new visit offers the remaining changes. It needs a clean saved checkpoint before it applies them. Your unfinished work stays where it is.

You can update directly to this release. What `/maintain` then does:

- **Old build paths.** The kit no longer uses build paths, including private exploration. `/maintain` shows your old section and the proposed risk record before it asks to move it. With your approval, it preserves your risk areas, acceptance dates and words. `Sensitive areas` becomes `Risk areas`. The earlier path and reason stay as history.
- **Open pieces.** The move adds risk areas to open pieces where their recorded reach identifies them. Checks report missing information rather than claiming a pass. The visit then asks the three risk questions to complete the record. If you decline, the kit leaves the old section unread and offers the move again on a monthly visit.
- **Repository.** Every project now needs a GitHub repository with issues turned on, and a session that can read and write them. Setup also checks branch protection and the tools the recipe needs for host and database access. Branch protection is the GitHub setting that holds a change until its checks pass. A private repository on GitHub Free can continue with a local push guard. On that plan, GitHub cannot enforce the project check. If your project was private only, `/maintain` explains the new expectations when it moves the project. It does not move the tool online.
- **Pull requests.** All builds now use pull requests.
- **New fields on pieces.** A newly shaped piece needs a `Risk areas:` line. Write `none` there when no area applies. On projects with code, the piece also needs a `Reaches:` line. This names the files and other parts the change can affect. `/shape` prepares both lines before it marks a piece ready.
- **Safety settings.** `/maintain` offers newer safety settings, and each missing or older project check, one at a time. These cover secret, test, review and push checks. It also asks which access setting your tool needs. Recording that choice does not change live access. `/setup-hosting` changes live access only with your approval.
- **Recipe names.** Older recipe names still work. `/maintain` can update those names, or open a piece for a larger recipe change.
- **Retired skills and pointers.** `/maintain` offers to remove retired skills. It also offers to correct the kit's command list and file pointers. It leaves your own wording for you to change.
- **Old plan list.** If your project still uses `plan.md`, the monthly routine offers to move each row into an issue. It removes the old list only after the issues exist.
- **Ready label.** If your project has no `ready` label, the routine marks the shaped pieces that qualify as ready. Pieces that wait on questions stay as they are.

**Command names.** The six commands from v0.20.x keep their names. These names changed:

- The background skill `change-triage` is now `triage`.
- The background skill `section-builder` is now `build-piece`.
- The background skill `grilling` is now `clarify`.
- `/start` is now `/setup-ai-build-kit`.
- `/build` and `/plan` give way to `/shape`, which agrees the work, and `/implement`, which builds it.
- `/fix` uses those same two commands.
- `/queue` is now part of `/implement`.
- `/sync` is now part of `/maintain`.
- `/ship` is now `/setup-hosting`.

## What changes

1. **Setup uses a pinned starter and requires approval before uploading code.** It prepares the local project and saves a checkpoint. Supported recipes use a specified starter version.
2. **Recipes configure new tools for private access by default.** Their access checks compare the live settings with the recorded choice. You can choose public access after hearing the risks.
3. **Risk areas on every piece.** Each piece names the risk areas it touches. You hear the caution once. You can accept the risk, and the kit records your words and the date. Acceptance lets the work continue. A run without you present cannot accept for you.
4. **Deciding is separate from building.** `/shape` records your decision and finishes the piece. Accepting a risk or an unchecked fact does not start a build. You ask `/implement` to build it.
5. **Build checks cover affected code and test effectiveness.** The kit checks what else a change touches and verifies that new tests fail before the change and pass afterwards. Project checks catch silent test edits and review findings that nobody resolved. A review names the exact saved version it read. The kit reports a review it cannot verify as unverified.
6. **Required checks block merging when they fail or cannot run.** Results distinguish passed, failed, could not run, could not decide and did not apply.
7. **Launch checks from the recipe.** Hosting uses the recipe's launch checks. A recipe launch requires a confirmed backup and a rollback procedure. `/setup-hosting` applies database changes with your approval before merging. Without a recipe, the kit records your choice after one notice and helps by hand. The recipe guarantees and automated launch checks do not apply.
8. **Optional longer runs.** You can approve longer runs, parallel builds or automatic merging, with limits that the kit records. Automatic merging leaves out repairs, and changes to risk areas, database structure or live settings. Required checks still apply.
9. **Every `/maintain` visit checks for updates and configuration gaps.** `/maintain` now looks for a newer release on every visit, and offers each newer version once. It also scans for secrets and checks branch protection. It reports gaps in the live copy and offers `/setup-hosting` to repair them.

## What was tested, and what is not proven yet

- We replayed 111 scripted conversations against this release and against v0.20.3, with the same model. By the test's rule, no case got worse.
- Founding now reaches its checkpoint in cases that stopped before.
- In the database-change replay, the change was applied after approval. v0.20.3 did not apply it in that test.
- The kit's checks, all 93 shell rehearsals and the release build pass on a clean copy.
- Some founding runs still save work in more pieces than planned, or fail to divide the plan into pieces. v0.20.3 has the same limits.
- When the starter command is blocked, founding stops and asks. This is by design.
- Runs on real hosting accounts were not part of this release's checks. The recipes' access steps have not yet been tested in a real run.
