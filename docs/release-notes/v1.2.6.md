v1.2.6 protects unfinished work during recovery and review, checks for changes to installed skills before later updates, and records existing behaviour before the kit changes an adopted tool.

**Who gets what.** Projects that update get the changed skills. Claude Code projects are offered six new safety rules; other coding agents follow the shared instructions or their own command settings. The browser-test and database-check changes apply to new projects using the recipe starter. Updating does not replace an existing project's browser configuration or check workflow, or install the workflow's new helper scripts.

## Updating

Run `/maintain` in an existing project. It names the new version, summarises these notes and asks for approval before updating. After installation, start a new session or reload the plugin where supported, then run `/maintain` again to finish the update. The update does not change your tool's data.

For the first upgrade from v1.2.5, the automatic local-edit check is not yet installed. Before approving replacement, save a project checkpoint and a separate copy of the installed skills, including plugin files outside the project and the targets of skill-folder links. Download and extract the archive from the [v1.2.5 release](https://github.com/gwpicard/ai-build-kit/releases/tag/v1.2.5) into another folder. From that extracted release folder, run:

```sh
diff -qr .agents/skills /absolute/path/to/installed/skills
```

Replace the last path with your installed skills folder: `.agents/skills` or `.claude/skills` for shared skills, the plugin's `.agents/skills` for Claude, or `agent-plugin/skills` for Agent Plugins. Repeat for each installed copy. The comparison lists changed, added and missing files, including committed edits; it may also list generated caches or unrelated skills. Exit 0 means no differences, 1 means differences, and 2 means it could not finish. Resolve read errors and review every difference before replacement. Keep local rules in `AGENTS.md` or preserve them separately. Later `/maintain` updates use the automatic check; direct installer commands do not.

Accept the Claude safety-rule offer to add the six rules to your project's settings. If the project's safety hook stops the agent saving `.claude/settings.json` in Git history, save it yourself. First confirm that no other files are staged for a commit. In Claude Code's chat, type this exact line, including the leading `!`:

```text
! git add .claude/settings.json && git commit -m "Add newer kit safety rules"
```

The rules apply on this computer before that save; the command records them in the project history. Declining the update leaves the current settings in place. Claude's rules block all forms of `git restore` and `git clean`, including unstaging and dry runs. Use `git reset HEAD -- <path>` to unstage while keeping the file, and `git ls-files --others --exclude-standard` to list untracked files.

Hosting checks that use Docker, including taking backup dumps, testing a restore and checking a container, now need a local Docker engine reached through a Unix socket. TCP and SSH Docker connections are refused before a check starts, with a message explaining how to continue. Select a local Docker context for these checks, or run them on another computer with a local engine.

For an adopted tool, establish tests for an uncovered area before the next edit to it. Keep its masterplan entries as `as found` until passing tests cover each entry, then record the evidence as `covered as found`. The update does not convert existing entries automatically, and a passing test does not approve a known fault.

## What changes

1. **Unfinished work stays in place.** During recovery and maintenance, the agent must leave your unsaved files where they are, even if you ask it to discard them. It offers to keep them or save a separate checkpoint through `/what-now`, and explains how you can discard them yourself in your editor and what would be lost. It must not try blocked commands or suggest allowing them. Claude's new rules also block stashing work out of sight. Read-only maintenance can continue while steps needing a clean checkpoint wait.

2. **Reviews protect existing work.** The review guard now snapshots files under review and pre-existing unsaved work, including staged changes, and restores them if a reviewer changes them. It reports other changes and any limit that prevents restoration. If a folder link would redirect restoration, the guard refuses it and keeps the snapshot for recovery. Directories and submodules are reported as skipped. This protection also covers the masterplan review at founding.

3. **Later updates check local skill edits.** After v1.2.6 is installed and reloaded, `/maintain` checks installed skills against recorded released copies before offering replacement. It names changed, added and missing files, including committed edits, and requires approval naming those files before replacing or recreating them. If the release record or file inventory is unavailable, replacement stops. Untouched shared installations are recognised, including the starter's generated type reference; ordinary generated caches do not trigger an edit warning.

4. **Tests before changing an adopted tool.** Adoption keeps the existing language and test runner. The kit first records tests for who can see and change records, then for the main tasks people perform. It checks that the original code remains unchanged while establishing that baseline and keeps the tests running for later changes. Areas it cannot test remain named and untouched until separate work makes them testable. The report distinguishes recorded behaviour from approved behaviour, so an existing fault does not become acceptable because a test preserves it.

5. **Hosting checks clean up their Docker resources.** Backup, restore and container checks label the resources they create and remove their own resources after success or failure. `/maintain` offers removal of labelled leftovers older than a day, with approval for the named resources; it leaves unlabelled resources alone. Restore now leaves the project's local database running. Its temporary copy still needs the default local ports, including 54322. If a port is occupied, the check cannot run: leave the other service running until its owner can stop it safely, or use another computer with those ports free.

6. **New starter checks use separate test resources.** New recipe projects get browser checks that select a free local port, honour a valid `PORT` setting and refuse to reuse an existing server. Their database checks also use labelled resources and clean up after themselves. Existing projects keep their own check files; adopting these changes requires a coordinated update to the workflow, browser configuration and helper scripts. Separately, the local fallback for GitHub checks no longer inherits a credential for a workflow binding whose GitHub token is unavailable.

7. **Clearer limits in the documentation.** Risk guidance now makes clear that accepting a caution does not start implementation during `/shape`; building still waits for `/implement`. The philosophy explains the kit's purpose through building, customising, owning and maintaining software. The new plain-Postgres template, jobs, file storage, company sign-in and handover format remain outside this release.

## What was tested, and what is not proven yet

- GitHub's source checks and site build pass. The last full rehearsal passed all 106 checks.
- Claude replays covered five runs each of the unsaved-work scenarios 48, 76, 78, 79 and 81, and three each of review and update scenarios 62, 70 and 80. The person's work survived every unsaved-work run. In the first five runs of scenario 78, the agent tried blocked commands in two runs and once suggested allowing them. After the fix, it followed the recovery rule in five of five runs. Scenario 76 also explained how the person clears their own work in five of five further runs, though other explanation gaps remained.
- Update rehearsals on four older test beds kept the person's work in place and uploaded nothing in all four. Minor explanation gaps remain recorded for later work. These runs do not prove every project check passed or every update step finished.
- No new real run of either hosting recipe was made for this release, by the maintainer's decision. Each recipe's `PROVEN.md` records the changed backup, restore, container and starter database steps. Backup and restore remain untried in a real run; earlier recipe evidence does not prove the changed steps. The adoption tests detect a planted permission fault, but no replay has measured whether an agent follows the adoption conversation.
