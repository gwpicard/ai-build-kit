v1.2.3 makes the billing fallback for `/merge` available in every installation, and corrects documentation that claimed more than the kit's checks verify.

**Who gets what.** Every project that updates gets the billing fallback. The other two changes affect the kit's README, its documentation and its documentation site. The only project they touch is one founded from a whole copy of an earlier release, which keeps an old copy of `WORKFLOW.md` that `/maintain` offers to remove.

## Updating

Run `/maintain` in an existing project. It names the new version, summarises these notes and asks for your approval before it updates, on a clean checkpoint. After the update, start a new session, so the agent reads the new skills. No other action is required. The update does not change your tool's data, and `/maintain` asks for your approval before any other change to the kit's files in your project.

## What changes

1. **The billing fallback ships with `/merge`.** When a GitHub billing limit stops `project-check` from starting and no other check is blocked, an approved merge can run that check's commands on your computer instead. Until now, `/merge` pointed to these instructions in the kit's `WORKFLOW.md`, which a project installed through the plugin or the skills installer does not have. The instructions are now part of the `/merge` skill, so every installation has them.

   The agent now describes the local run more exactly: the workflow's commands run on your computer against a clean copy of the exact commit, and your computer's own tools replace setup actions such as installing Python. It tells you this before you approve and again after the run. As before, the local run must pass, and any other failed, pending or missing check blocks the merge.
2. **The user guide moved to the documentation site.** `WORKFLOW.md` is removed from the kit. Its guidance is now on the documentation site, which has new pages on working with other people, maintaining your tool and live data. Links that pointed to `WORKFLOW.md` now point to the site. The README is now a short introduction with the commands, the installation steps and links to the site.

   A project founded from a whole copy of an earlier release still holds its copy of `WORKFLOW.md`. As before, `/maintain` offers to remove that copy with the kit's other leftover files if you have not changed it.
3. **Documentation that matches the checks.** The README, the documentation and the site described some behaviour more strongly than the kit's checks support. For example, they said a recipe's launch script requires a confirmed backup before a launch. The script blocks recording the live address until a backup is confirmed and the recipe has a way back, which on a later launch must be an earlier build listed on the host. It cannot stop a host that deploys on merge. They also did not say that restoring a backup has not yet been tried on either recipe. Those passages now say what each check does.

   The promises list now names the evidence for each promise: the check that enforces it, or a note that the promise rests on judgement or on a scenario not yet replayed. The site's rules, recipes and agent limits pages are now generated from the repository's documents, so the site shows what those documents say.

## What was tested, and what is not proven yet

- On GitHub, the source checks, the site build, the site's link check and all 101 rehearsals pass, including the recipe database checks.
- The mutation check, which breaks one promise at a time, ran on the documentation rework before this release's last wording fixes. It found no break that the checks missed.
- The release archive was built, and the starter and plugin rehearsals pass with it.
- No conversation was replayed for this release. The skill changes move the billing fallback into `/merge` and describe its local run more exactly, remove the build limits' link to `WORKFLOW.md`, and reword the `/maintain` description.
