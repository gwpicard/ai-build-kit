v1.2.2 fixes two problems that made the kit ask or report more than it should: a live change that needed approval twice, and an update that called the kit's own documents yours.

**Who gets what.** Every project that updates gets the approval fix in item 1. Item 2 applies only to projects founded from a whole copy of an earlier release, such as v1.0.0 to v1.1.2, which hold copies of the kit's documents in `docs/`. Item 3 changes the kit's README and documentation site, not your project.

## Updating

Run `/maintain` to update an existing project. Then start a new session, so the agent reads the new skills. No other action is required, and no project data changes.

## What changes

1. **One approval for one live change.** Before, the agent could record your approval under a name the recipe step did not look for, or use it up before the step ran. The step then refused, and you were asked to approve the same change again. Nothing changed without approval, but the second request was a fault.

   Now only the step that makes the change uses the approval, and it recognises the approval whether or not the agent included the script's folder or its `.sh` ending in the name. When a step finds no approval, it shows any unused approval with a similar name, with the words you used, so the agent can check whether it already covers this change instead of asking again. Each approval still covers one named change, once.
2. **The kit's own documents are no longer treated as yours.** Projects founded from a whole copy of an earlier release hold copies of documents such as `docs/COMPATIBILITY.md`, `docs/SOURCES.md` and `docs/PHILOSOPHY.md`. After an update, `/maintain` called each one "a document of your own" and listed every outdated reference in it, up to 84 lines on every visit.

   Now `/maintain` recognises a copy that matches a released version exactly and offers to remove it with the kit's other leftover files. A copy you edited stays, with one sentence saying that it started as the kit's document and was changed. A document of your own in `docs/` is still left alone, because nothing is removed unless it matches a released copy at the same path.
3. **A clearer introduction to the kit.** The README and the documentation site now open with an image and a "Why this kit" section. It compares the kit with hosted app builders and with developer skill sets, and it says what is tested and what is not proven yet. The site has new colours.

## What was tested, and what is not proven yet

- The source checks, the adapter checks and the full set of rehearsals on a clean copy pass on GitHub.
- A replay of two recorded live-change conversations confirmed that the agent asked once, and that each change was applied once after one approval.
- The kit's update was run with an agent on copies of four projects founded with v1.0.0 and v1.1.2. In all four, the update kept unfinished work, uploaded nothing, saved the kit's changes on a separate local branch, and identified the kit's documents correctly.
- The same runs found two problems that this release does not fix. In one project, the save the person approved for the kit's changes also included a build file, `tsconfig.tsbuildinfo`, and a changed setup path in `.agents/tools/codex-setup-path`. On the second visit, the agent sometimes stated facts about GitHub or hosting without reading them again.
