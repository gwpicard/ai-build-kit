The run used a throwaway private app on a Hetzner cpx22 server running Coolify 4.3.23, set up by the coolify-devops 0.4.0 companion. The app had no domain. It ran on the internal lane, reached over the team's private network through a Tailscale Service that docktail registered. The Supabase Free plan had no room for a second active project, so previews and live shared one Supabase project on this run.

Preview: Previews were off on the new app, and Coolify answered the first pull request with "Preview deployments disabled." The companion's tools refused the setting, and the run missed the Enable preview deployments button on the Preview Deployments page, so the operator's session on the server switched previews on through Coolify's API. A pull request then built into its own container on its own commit, which passed Coolify's health check. Read on the server, `/api/health` gave 200, `"database":"ok"` and the pull request's commit. The app has no domain, so the preview got no address, it was not registered on the private network, and the person could not open it. The companion's maintainer reads Coolify's own code as confirming both: a pull request deployment replaces the app's custom labels, and a preview address needs a domain. After the pull request closed, Coolify's delete job finished within 9 seconds, and the container was seen gone at 27 seconds. This run did not try a preview address on an app with a domain, `{{pr_id}}.{{domain}}`; the second run, below, did. That previews stay off the live database is not proven by this run, since previews and live shared one project.
Going live: The hosting request's answer gave the app no host port and Coolify's own container name. A merge into `main` deployed through the GitHub App in 64 seconds, as a rolling update that swapped the container once its health check passed. The check was on for `/api/health`, port 3000 and host `127.0.0.1`, and healthy. That Coolify's check is off by default was not seen, since the companion created the app with it on. `SOURCE_COMMIT` reached the container, and `/api/health` on the live address gave 200, `"database":"ok"`, and a commit equal to the merge commit on `main`. The migration, the row-level security query and the local container check had already run on the person's machine, and these pull requests carried no new migration, so they were not repeated.
Rollback: Before the nightly cleanup, the Rollback page listed three kept images, not two. The control was hard to find, on the app's Rollback page in its Operations section. The person could not find it, so the orchestrating agent clicked Roll Back To This Image on the earlier commit, in the Coolify page. Nothing the kit or the companion's tools could call did it. The click redeployed its kept image with the build step skipped, and `/api/health` gave the earlier commit. A read within the first 30 seconds still showed the newer commit, while the old container served. A deploy of `main` then rolled forward, again from a kept image.
Backup: Not run again here. Backup is a shared part proven once, and as the recipe format allows, its outcome comes from the Vercel recipe's real run on the same part.
Restore: Not run again here. Restore is a shared part proven once, and as the recipe format allows, its outcome comes from the Vercel recipe's real run on the same part.
Secrets: Both names in `.env.example` were set in Coolify for build time and run time, each as a live row and a preview row, and the pasted list carried no value. No public name carries a secret, and no value is in the repository or the Dockerfile.
Logs: The container's output since the deployment held no error lines. The build log held two routine lines from Coolify itself, a missing build helper container and an orphan container warning during the rolling update, and none from the app.
Health: Coolify's check against `127.0.0.1:3000/api/health` passed on every deployment. Coolify's source shows the check runs `curl` and falls back to `wget`, and the `node:22-alpine` image has only `wget`. From the person's machine over the private network, `/api/health` gave 200 with `"database":"ok"`.
Access: No real run yet. The section was added on 2026-10-14. Neither Coolify's password in front of the app, which it calls HTTP Basic Authentication, nor the pasted answers from outside and inside the private network have been tried, and the shared sign-up commands have had no real run in either recipe. The first run above did reach the app only over the team's private network, which is the gate private relies on there.

A second run, on 2026-09-27, tried the public lane. It used a throwaway private app on a Hetzner cpx32 server running Coolify 4.3.23, pinned by hand for the run and pinned in coolify-launchpad 0.1.1. coolify-launchpad also installed the coolify-devops companion; its latest release was 0.4.0, but the installed version was not recorded. The app had a domain, a DuckDNS name, with ports 80 and 443 open. The Coolify dashboard was reached over the private network, and port 8000 was open only to GitHub's webhook ranges. The GitHub App was made by Coolify's manual route, with a webhook secret. Previews and live shared one Supabase project on this run by choice. The Supabase organisation held no other project, so a second project could have existed, and the recipe's path with a preview project was neither followed nor tried.

Preview, public lane: Previews were off on the new app, and `/host` asked the person to press the button. The person could not find it from the path `/host` gave, "Previews -> Preview settings". The orchestrating agent found the button and pressed it, at the person's request: the app's left menu item Preview Deployments, then the Preview settings card, then Enable Preview Deployments at the card's top right. After a reload the button read "Disable preview deployments". The template was `{{pr_id}}.{{domain}}`, and Coolify showed the pattern `{{pr_id}}.<app domain>`. `/host` made the preview rows in Coolify's preview view, and they were filled before the preview built. A pull request opened at 01:49. By 01:50:31, `https://1.<app domain>/api/health` gave 200, `"database":"ok"`, the pull request's commit and the live project's reference, with a Let's Encrypt certificate for that preview host. The pull request merged at 01:50:43. By 01:50:51 the preview address answered 503 with Traefik's "no available server". A later read on the server showed no preview container left. That previews stay off the live database is still not proven, since the project was shared.
Going live, public lane: `/host` gave the app a domain on the public lane, a Dockerfile build, port 3000, no host port, and the health check on `/api/health` at `127.0.0.1:3000`. The first build took 53 seconds, and the app was running and healthy. From the maintainer's machine, `/api/health` on the live address gave 200, `"database":"ok"` and a commit equal to `origin/main`. The name had a Let's Encrypt certificate, and http redirected to https. The merge then deployed through the GitHub App's webhook, with the secret set: `/api/health` gave the merge commit at 01:51:22, 39 seconds after the merge.
Not tried on the second run: rollback, backup, restore, logs, the settings the kit can read, and the local container check. Secrets and health were not recorded as checks of their own, though Coolify showing the app running and healthy covers part of health.
